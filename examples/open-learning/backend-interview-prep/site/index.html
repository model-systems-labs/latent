10 minute lesson

Run a visible reasoning loop

Use a five-move loop to clarify, frame, execute, validate, and improve without disappearing into silent analysis.

The downloaded recruiting brief divides the technical interview into roughly 20 minutes of system design concepts and 30 minutes of backend coding. Its strongest process signal is breadth before depth: show familiarity across the landscape, then follow the interviewer's interest into detail. Public Karat guidance likewise recommends practicing under time pressure while explaining your thought process aloud.

The five-move loop

  1. Clarify: ask one question whose answer could change the design or implementation.
  2. Frame: state the goal, important constraints, assumptions, and your starting approach.
  3. Execute: build the solution in visible increments and name decisions as you make them.
  4. Validate: test the happy path, boundaries, failure modes, and operational behavior.
  5. Improve: only after the baseline works, add optimization, scale, or refactoring.
Ask a question that changes something

Prefer 'Must a successful write be immediately visible to later reads?' over 'How many users are there?' when only the first answer changes your consistency design. Explain what decision the answer controls.

Narrate decisions, not keystrokes

  • I see two viable approaches; I am weighing consistency against write availability.
  • I will start with the simplest complete request path, then identify its first bottleneck.
  • This change stays local because the surrounding contract is not part of the task.
  • Let me test duplicates, missing data, and a dependency timeout before I optimize.
Prepare three experience anchors

Have one factual story about scale, one about reliability, and one about a difficult code change. Use context, constraint, decision, tradeoff, observed result, and what you would change now.

You are asked to design an order API. Which opening question gives the strongest design signal?

The consistency question exposes a user-visible invariant that can change storage, replication, and read-routing choices. A framework preference is usually downstream of the design, while demanding every detail prevents progress under time pressure.

18 minute lesson

Choose architecture from the pressure points

Move from requirements and access patterns to components, data guarantees, and explicit architecture tradeoffs.

A strong system design answer is a sequence of justified decisions. Start with the behavior and constraints, sketch one complete request path, and then pressure-test the parts most likely to fail. Technology names are useful only when they answer a requirement.

A 20-minute structure

  1. Minutes 0-2: clarify the core use case, scale, latency, consistency, security, and scope.
  2. Minutes 2-4: estimate traffic and data only enough to reveal the hot path or likely capacity limit.
  3. Minutes 4-8: sketch the client, API, service boundary, storage, and end-to-end request flow.
  4. Minutes 8-14: cover storage, indexes, consistency, caching, asynchronous work, and security.
  5. Minutes 14-18: pressure-test dependency failure, retry storms, hot keys, deploys, and observability.
  6. Minutes 18-20: summarize the choice, its largest risk, and the first scale step.

Model data from invariants and access patterns

  • List the primary entities, read keys, filters, sorts, aggregations, and update patterns.
  • Name what must never be duplicated, lost, oversold, or observed out of order.
  • Choose transaction boundaries and isolation based on concurrent operations, not habit.
  • Add an index for a demonstrated access path and acknowledge its storage and write cost.
  • Choose a partition key that distributes load without making essential queries scatter everywhere.
Do not design from nouns

A queue, cache, service, or NoSQL database is not automatically scalable. State the pressure point it addresses and the new correctness or operational cost it introduces.

Tradeoff sentences

  • Begin with a modular monolith when one team benefits from simple transactions; extract a service when scaling, ownership, or deployment needs diverge.
  • Use synchronous work when the caller needs the result now; use asynchronous work for slow, bursty, or retryable work whose completion can be observed later.
  • Prefer stronger consistency when stale state violates an invariant; accept bounded staleness when availability and latency are more valuable.
  • Use relational storage when constraints, transactions, relationships, and flexible queries dominate; consider other models only after access patterns justify them.
A table receives heavy writes and one new endpoint filters by status and creation time. What is the strongest index proposal?

PostgreSQL documents both the read benefit and system overhead of indexes. The strongest answer ties one candidate index to a real access path, validates it with the query plan and workload, and accounts for write cost rather than indexing everything or nothing.

18 minute lesson

Pressure-test security, performance, and failure

Identify the important trust boundary and bottleneck, then use precise controls for access, overload, retries, and monitoring.

Security, performance, and reliability are boundary questions. Who crosses this boundary, what shared resource can be exhausted, and what happens when the next dependency is slow or unavailable? Cover the highest-risk case in each category before adding detail.

Security: identity is not permission

  • Authentication establishes an acceptable identity; authorization decides whether that identity may perform this action on this resource.
  • Perform resource-level authorization on the server for every protected path; a hidden control in the client is not a security boundary.
  • Validate input shape, size, and allowed values, and use parameterized queries rather than concatenating untrusted data.
  • Minimize sensitive data, protect secrets, redact logs, and record safe audit events for important actions.

Performance: measure the user-visible path

  • Define throughput and p50, p95, or p99 latency targets together with errors and resource ceilings.
  • Instrument request time, dependency time, query plans, CPU, memory, queue depth, and cache hit rate.
  • Locate the constraint before adding a cache, queue, replica, partition, batch, or concurrency.
  • After a change, repeat a representative load test and watch for the bottleneck to move.

Reliability: retries need a budget

  • Use timeouts to bound waiting and leave time for the caller to handle failure.
  • Retry only transient failures and safe operations; cap attempts and use exponential backoff with jitter.
  • Make side-effecting operations idempotent or deduplicate them before treating retries as safe.
  • Use backpressure, rate limits, circuit breaking, and load shedding to stop one failure from consuming all shared capacity.
Use the four golden signals

Google SRE frames monitoring around latency, traffic, errors, and saturation. In an interview, name the user-visible symptom, the dependency or resource behind it, and the alert that should lead to action.

A client times out while creating a payment and cannot tell whether the server committed it. What is the strongest retry design?

An idempotency key lets repeated attempts recover the first logical effect instead of creating duplicates. Bounded backoff and jitter reduce synchronized load, while tight loops amplify failures and a blanket ban on retries gives up useful recovery behavior.

20 minute lesson

Build the simple endpoint first

Turn a request into a clear contract, implement the happy path, and then layer in validation, authorization, errors, and tests.

For a new feature or endpoint, make the contract visible before code. Confirm the input, output, persistence effect, duplicate behavior, missing-data behavior, authorization rule, and expected dependency failures. Then implement the smallest complete request path and harden it in deliberate layers.

The coding sequence

  1. State the request and response contract, one important assumption, and the proposed control flow.
  2. Implement the happy path with direct control flow and names that expose intent.
  3. Add input validation and resource-level authorization at the boundary.
  4. Protect invariants with a database constraint, transaction, version check, or idempotency record as appropriate.
  5. Map expected failures into stable public errors without exposing stack traces or sensitive data.
  6. Run a happy-path example, boundaries, and one dependency failure; then discuss complexity and the next improvement.

A create-order contract

Application checks do not close every race

A read-then-create check can let concurrent requests both proceed. Place critical uniqueness and concurrency guarantees at the storage boundary, then translate the resulting conflict into the public API contract.

Error categories

  • Caller error: invalid input; respond with safe, actionable validation details.
  • Authentication or authorization failure: reject without leaking sensitive resource information.
  • Domain conflict: explain that current state prevents the operation and whether the caller can retry differently.
  • Transient dependency failure: bound waiting, retry only when safe, and preserve a request identifier.
  • Unexpected failure: return a stable server error, record structured internal context, and emit a metric.
Which implementation order best matches a simple-first backend interview approach?

This order produces a working observable baseline early, then layers in correctness at the boundaries. Generic abstractions and performance mechanisms are justified only after the contract and pressure points are known.

16 minute lesson

Change existing code without widening the blast radius

Map the current contract, make the narrowest coherent change, and prove the behavior at the most useful boundary.

Existing code carries contracts that are not obvious from one function. Read before changing: inspect signatures, types, tests, call sites, side effects, configuration, persistence, and nearby error behavior. Your goal is the narrowest coherent change that preserves unrelated behavior.

A safe-change loop

  1. Reproduce or restate the requested behavior in one concrete example.
  2. Locate the public contract and the smallest implementation boundary that owns it.
  3. Read nearby tests and callers to discover compatibility and error expectations.
  4. Make the minimal code change using local conventions and explicit side effects.
  5. Add a regression test at the boundary where the defect could escape.
  6. Run focused checks and inspect the final diff for accidental formatting, generated files, or API changes.
Characterize before refactoring

When behavior is unclear, capture the current externally visible behavior in a focused test. That evidence gives you a safer base for the requested change and makes any intentional contract change explicit.

High-value edge cases

  • Empty input, one item, maximum allowed size, duplicates, and deterministic ordering.
  • Missing record, stale version, unauthorized tenant, and conflicting concurrent update.
  • Dependency timeout, partial response, cleanup after failure, and retry after an ambiguous result.
  • A migration deployed before and after the application version that consumes it.

Code quality as decision quality

  • A reader can name each unit's responsibility without tracing hidden state.
  • Dependencies and side effects are explicit enough to test and replace.
  • The abstraction earns its complexity by representing a stable repeated concept.
  • Logs, metrics, and errors help diagnose behavior without exposing secrets.
  • The test proves the contract and would fail if the regression returned.
A bug report points to one endpoint, but the shared helper it calls has unclear behavior and many callers. What is the strongest first move?

Reproduction plus a boundary test establishes the behavior that matters and exposes the blast radius before editing shared code. A cleanup-first rewrite or copied logic increases change surface without first proving the requested outcome.
