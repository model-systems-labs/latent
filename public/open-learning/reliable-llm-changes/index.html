Make reliable changes to an LLM application

A compact lesson and review pack for turning a proposed LLM application change into explicit claims, representative checks, and an inspectable release decision.

12 minute lesson

Write the claim before the metric

Begin with the behavior that must remain true, then select a check that could reveal a meaningful failure.

An evaluation is useful when it can change a decision. Start by naming the behavior you expect, the situation in which it matters, and the evidence that would make you withhold a release. This keeps a convenient metric from quietly becoming the goal.

Separate the claim from its proxy

  1. Claim: the assistant keeps a user's stated constraint while revising a plan.
  2. Failure condition: a revised plan drops or contradicts any explicit constraint.
  3. Proxy: the share of representative revision cases in which every constraint is preserved.
  4. Release rule: investigate every failed case and do not release if a critical constraint is lost.
A score is not the behavior

A high average can hide a severe failure in a small but important slice. Keep the individual cases available for inspection.

Which statement is the strongest release claim for a plan-revision assistant?

The constraint statement names the behavior, the situation, and observable evidence. Latency measures a different property, while an unstructured preference does not define the failure that matters.

15 minute lesson

Build evidence that can say no

Use representative cases, inspect failures, and record a decision that another person can reproduce.

A useful test set represents how the feature will actually be used, including ordinary cases, boundary cases, and the failures that would carry the greatest cost. Keep the set small enough to inspect at first. Add cases when production evidence reveals a new failure mode.

Read the shape of the failures

  • Check the aggregate result for broad regression.
  • Read every critical failure rather than treating it as a rounding error.
  • Compare important slices, such as short and long conversations or familiar and unfamiliar topics.
  • Record the tested version, the cases, the result, and the person or process that made the release decision.
Prefer evidence over machinery

A simple test that catches the failure you care about is more valuable than a complicated evaluation system that produces a number nobody can interpret.

A new prompt improves the overall pass rate from 88% to 94%, but two high-cost safety cases now fail. What is the strongest next step?

The aggregate improvement does not cancel a known critical regression. The release decision should reflect the severity and location of failures as well as the overall score.
